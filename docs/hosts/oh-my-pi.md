# Oh My Pi host

Oh My Pi (OMP) is the implemented host integration. `host-omp` is Runtime-Preset-neutral and has no dependency on Persona, Evolution, structured-inference providers, CodeGraph, memory, SQLite, embedding, vector packages, or a named preset.

## Activation

The neutral `@doppelganger/doppelganger-omp` entrypoint resolves generic host options, validates optional non-empty `DOPPELGANGER_ACTOR_ID`, and delegates to `createDoppelgangerOmpExtension`. The repository-local `.omp/extensions/doppelganger.ts` only re-exports that package entrypoint. Runtime Preset selection discovers the nearest `.doppelganger/manifest.yaml` from the working directory up to the Git root and follows strict precedence:

1. explicit host/session Runtime Preset;
2. project `runtimePreset`;
3. user `defaultRuntimePreset`;
4. optional deployment default.

OMP's normal roster configuration uses the shipped actor-neutral `standard` deployment default. First selection from an uninitialized home creates `config.yaml`, an empty `runtime.cordis.patch.yml`, and `.runtime-presets/`, then activates `standard` without copying its package-owned assets; later starts preserve user edits. A winning missing or broken preset fails visibly and never falls through. Deployments that intentionally disable the shipped root or otherwise configure a defaultless roster can still leave OMP inactive; that state keeps OMP fully usable and exposes initialization that writes only `version` and `runtimePreset` to the project manifest.

`runtimePresets` host options configure the pure roster's roots, trust, derived shipped/user roots, and optional deployment default. OMP does not compose the Cordis roster plugin into the child and does not implement a second discovery path.

`actorId` is host configuration, not selection, Persona configuration, or a Runtime Host field. OMP transports the validated immutable value in its activation envelope, then mounts a separate protected Actor Identity plugin in the child: bound when configured and explicit unbound otherwise. The actor-neutral shared bridge neither receives nor infers it. The shipped `standard` and other actor-independent presets still activate. A memory-bearing preset fails visibly before memory storage or tools become active when the actor provider is unbound. Changing actors requires a new OMP Runtime Session.

## Extension discovery and ownership

OMP discovers extension candidates in this order: native project and user extension modules, ambient JavaScript or TypeScript hook factories, installed plugin entrypoints, then explicitly configured paths. It normalizes each candidate with `path.resolve()` and removes only repeated absolute paths. It does not deduplicate by npm package name, imported module identity, or exported factory identity.

The linked `@doppelganger/doppelganger-omp` entrypoint and this repository's `.omp/extensions/doppelganger.ts` delegation are therefore supported alternatives for one OMP invocation and profile, not two paths to enable together. The project file re-exports the package factory, but its own absolute path differs from the installed plugin entrypoint. If both paths are active, OMP binds two extension instances; each registers its handlers and may start its own child runtime. Setup and profile-scoped switching commands are documented in the repository README and configuration guide.

This boundary does not create global Runtime Session ownership. Each loaded adapter has an extension-local serialized coordinator, and each committed binding owns one isolated child Runtime Session. Doppelganger adds no process-wide singleton, lease, filesystem lock, or prohibition on several OMP processes opening the same OMP session; separate processes and separately loaded adapters retain separate child ownership.

## Process and transport

Each committed OMP runtime binding owns one Node child runtime and one framed JSON-RPC connection over stdio. Activation is an exact handshake: both sides require OMP RPC protocol version 4 and the same frozen closed actor-neutral Runtime Host protocol version 2 capability profile before any projection commits. The profile declares per-turn context delivery, dynamic tool catalogs, required approval, cancellation, and only the lifecycle event kinds OMP can forward faithfully. Unknown fields, missing identities, malformed schemas, unsupported capabilities, or version mismatch fail the binding instead of falling back to legacy payloads.

All portable descriptor schemas, invocation inputs, and results are admitted with the protocol-owned strict JSON contract before approval digesting, dispatch, or serialization. OMP host envelope/version/state checks remain host-owned. Invalid values are rejected without coercing through `JSON.stringify`, invoking accessors or `toJSON`, dispatching handlers, or consuming approval. Host lifecycle observations are the sole intentional exception: they are bounded and lossy-projected first, with truncation metadata, then strictly validated.

The private RPC surface is explicit: `session.activate`, `runtime.diagnostics`, `context.resolve`, `tools.snapshot`, `tools.invoke`, `tools.cancel`, `event.publish`, `omp.todo-reminder`, and `session.dispose`. Context requests carry a request ID plus `{ input, turnId? }`. Activation returns one revisioned tool catalog; `toolCatalog.changed` is the only runtime-to-host change callback and carries only a revision hint, after which the adapter fetches and validates `tools.snapshot` before replacing OMP proxies. Tool invocation carries call ID, exact tool revision, input, optional turn ID, and an optional one-shot approval grant bound to the canonical input digest. Abort requests use `tools.cancel` with the same call ID.

The binding captures its generation, OMP session ID, an opaque UUID-backed identity prefix, canonical working directory, adapter, projected descriptors, turn state, and lifecycle ordinals; asynchronous work may affect the host only while that exact binding remains current. The prefix is created once per binding, is not Runtime Session metadata or a logging activation ID, and does not require a persistent counter or a feature-specific service. `host-omp` resolves the private child entry relative to its own installed module layout; callers may override that path only through the explicit embedding/test seam. Its package contents include the child and every private runtime module the child imports.

One extension-local serialized coordinator owns activation, replacement, and shutdown. `session_start` establishes the initial binding. Post-commit `session_switch` and `session_branch` detach the old projection, neutrally dispose the old child, and only then activate a fresh binding for the new session ID and canonical working directory. `session_tree` retains the current child when both values are unchanged and uses the same replacement path when either changes. Only the latest requested generation may commit; failed replacement leaves ordinary OMP available without reviving the detached runtime, and stale child notifications, context results, lifecycle callbacks, and retained proxy closures cannot mutate or invoke a newer binding.

Notification observers are a contained boundary rather than a transport-failure boundary. Observers settle independently; one rejection is converted to a bounded method/message diagnostic, sibling observers still run, unrelated pending requests remain active, and failure in the diagnostic sink is also contained. The process owner records the diagnostic in its bounded stderr history and the OMP extension reports it without marking a healthy child failed.

The protected final patch appends three runtime-owned plugins that authored input cannot forge or replace: actor identity, the generic Runtime Host bridge, and the OMP-native event bridge. The generic bridge shares the Runtime Session isolate realm with optional context, tool, capability, and lifecycle services. The OMP-native bridge remains separate from generic lifecycle and currently translates validated `todo_reminder` observations into the namespaced Cordis event `doppelganger/host/omp/todo-reminder`.

## Projection

Once before each user-initiated OMP agent run, the adapter resolves current assembled runtime context with a unique request ID and the owning binding's direct principal input and stable turn identity. It appends only the non-empty instruction-authority projection to OMP's existing `systemPrompt` through `before_agent_start`; host instructions remain ordered and unchanged. The data-authority projection becomes one synthetic user-role message with an explicit data-only warning and delimiters, never a system or developer message. OMP's `context` hook appends that transient message to each model request in the same run, including tool continuations, without mutating the supplied message array, persisting session history, or re-resolving providers. The snapshot is cleared when the turn ends or its binding is replaced.

Runtime tool JSON Schemas are validated and translated to OMP parameter schemas. JSON Schema `default` values remain annotations: OMP validates caller-supplied arguments but does not materialize omitted values, so mutable defaults such as arrays cannot become shared host state and the portable handler or upstream server remains authoritative for defaulting. Dynamic proxies are replaced only from a complete validated catalog snapshot; removed definitions become inactive, and each closure remains bound to the binding, portable name, and descriptor revision that registered it. A stale closure or descriptor revision fails before the portable handler. OMP abort signals issue call-correlated cancellation without weakening normal result validation.

Portable tools declaring required approval are projected as essential top-level OMP tools and become native write-tier prompts with a bounded deterministic rendering of the exact parsed arguments. When the descriptor includes a portable reason, OMP also supplies it as an advisory native prompt reason; required approval remains fully enforced when it is absent. Keeping required tools out of OMP's `xd://` discoverable transport preserves the tool-owned mandatory prompt even in permissive and `yolo` modes; portable tools without required approval remain discoverable. Only one explicit grant reaches `tools.invoke`; the runtime revalidates its call ID, tool revision, and canonical input digest and consumes it once before dispatch. Rejection, cancellation, unavailable UI, replay, stale revision, or changed input fails closed without handler invocation.

The dotted portable name remains the canonical tool identity and the exact value sent through `tools.invoke`. OMP exposes it as `doppelganger_` followed by each `.` separator replaced with `_`: `persona.inspect` becomes `doppelganger_persona_inspect`, `persona.revise` becomes `doppelganger_persona_revise`, and `runtime-plugin.inspect-list` becomes `doppelganger_runtime-plugin_inspect-list`. Portable names cannot contain `_`, so the projection is collision-free for valid descriptors and requires no reverse decoding. The complete OMP name may contain at most 64 ASCII characters; an overlong or defensively detected colliding descriptor stays unavailable with a visible diagnostic while unrelated valid tools remain projected. This is a clean cutover: callers must replace the removed hexadecimal separator encoding with `_`, and the adapter registers no legacy aliases or Persona-specific branches.

OMP lifecycle observations are normalized and forwarded to the runtime-side plugin using identities captured by the owning binding, never values reread from mutable OMP session state. Adapter-generated turn IDs, context request IDs, and lifecycle/native-event delivery IDs use the binding's identity prefix. Restarting OMP, switching away and back, or otherwise recreating a binding for the same logical session therefore cannot reuse its previous counter-derived identities. The logical `sessionId` and native `callId` remain unchanged; repeated delivery of an already-created event retains its original `deliveryId`. Same-binding tree navigation and child HMR retain the prefix and active-turn correlation. This identity strategy belongs only to the OMP adapter; portable consumers treat identifiers as opaque and do not parse the prefix. `tool_execution_end` is the sole source for bounded `tool-completed` results and errors. Final assistant content from `turn_end` becomes `turn-committed`; aggregate `turn_end.toolResults` are not copied or synthesized into lifecycle events. Callbacks that settle after their binding is detached are discarded. OMP's resumable `agent_end` and `session_stop` hooks do not fabricate `session-completed`; only committed turns are candidate-capture input. These generic context, tool, lifecycle, approval, and actor-binding paths do not require Persona or memory extensions.

OMP-native events remain outside lifecycle normalization. `todo_reminder` forwards bounded todo content, status, optional blocker, attempt counters, timestamp, session ID, and stable delivery ID through `omp.todo-reminder` on the existing per-session RPC connection; the runtime-side protected plugin validates the closed envelope and owning Runtime Session again before emitting the OMP-namespaced Cordis event. This does not add `todo-reminder` to the cross-host lifecycle protocol and does not imply support in another host.

An opt-in Dynamic Runtime Plugins Loader row registers seven ordinary portable `runtime-plugin.*` controls through the same child transport. OMP projects define, inspect, stop, and undefine through its discoverable dynamic path, while `runtime-plugin.run` is an essential top-level tool so its required one-shot prompt cannot be bypassed by permissive or `yolo` mode. The prompt includes the portable shell-equivalent warning and a bounded deterministic rendering of the exact immutable Package metadata. Generated tools and context use normal exact replacement; update, stop, undefine, owner replacement, and shutdown remove their effects, and stale OMP closures fail unavailable. A generated exception is returned as a domain tool error; a child crash follows the existing fatal child failure boundary and leaves OMP usable.

An opt-in Evolution Loader row follows the same generic path. OMP projects all seven portable `evolution.*` controls with its normal `doppelganger_` name transformation, contributes policy and reminder context through the once-per-user-run authority-preserving snapshot, exactly removes proxies after row removal, and requires no Evolution-specific adapter code. Its proactive worker consumes only the ordinary lifecycle events OMP already publishes; optional structured inference is another Runtime Preset service and adds no host RPC. Automatic and manual proposal controls are non-executing and declare no native approval; any later Persona revision or generated-code execution retains the owning tool's separate approval contract.
An opt-in CodeGraph Loader row also follows the generic path. OMP projects `codegraph.status` and `codegraph.explore` as discoverable `doppelganger_codegraph_status` and `doppelganger_codegraph_explore` devices, refreshes them after committed reload, and removes them after row removal without CodeGraph-specific routing, process, or index logic. The Runtime Session workspace supplied by OMP remains the only allowed graph boundary.
An opt-in MCP import row also follows the generic path. OMP session activation completes while configured MCP servers remain `connecting`; later successful discovery mutates only `doppelgangerTools`, producing the existing `toolCatalog.changed` revision hint and exact catalog refresh. Transport closure or configuration replacement removes the corresponding proxies through the same path. `host-omp` receives no MCP configuration, client, diagnostic snapshot, retry policy, or feature-specific status/UI contract and contains no MCP-specific production routing.

## Failure and shutdown

Invalid selection or structurally invalid Loader configuration, activation failure, fatal child transport failure, runtime failure, or child failure disables Doppelganger for the affected binding, reports a visible diagnostic, and leaves OMP usable. Feature-owned operational failures such as one MCP server's unavailable command, endpoint, timeout, protocol, or discovery error do not fail the child Runtime Session; they leave that server without tools while healthy portable services and later catalog changes continue normally. A contained notification-observer rejection reports its diagnostic but does not disable the runtime. The process owner preserves the concrete bounded child-exit reason for an in-flight RPC instead of replacing it with a generic transport closure. Replacement and shutdown use the same detach-first neutral disposal order: projected tools are withdrawn, `session-disposed` is published for the captured owning session when possible, Runtime Session disposal is requested, transport is closed, and child termination escalates when cleanup does not settle. `host-omp` does not preserve an old child or tool set after replacement failure.

## Package boundaries

`@doppelganger/doppelganger-omp` is the private, version `0.0.0` local install unit understood by OMP's plugin manager. Its manifest declares exactly one extension entrypoint. That neutral entrypoint supplies no home, child path, actor default, Persona instance, Evolution behavior, inference provider, CodeGraph behavior, logging destination, or named Runtime Preset; a non-empty `DOPPELGANGER_ACTOR_ID` is the only package-level host binding input. The package owns the product dependency closure required to resolve the shipped `standard` Runtime Preset and optional Dynamic Runtime Plugins, Evolution, Pi structured inference, CodeGraph, file logging, and Sentry logging from an isolated linked plugin tree. Installation alone activates none of the optional rows.

`@doppelganger/doppelganger-host-omp` remains the generic Runtime-Preset-neutral adapter library. Its only declared package entrypoint exports `createDoppelgangerOmpExtension`, `DoppelgangerOmpExtensionOptions` including pure-roster configuration, and the adapter-facing `OmpChildConnection`, `OmpChildDisposal`, and `OmpChildFactory` types. It has no dependency on Persona, SQLite, memory, embedding, vector, Dynamic Runtime Plugin, Evolution, structured-inference provider, CodeGraph, or named-preset packages. Child runtime, process owner, framed protocol, wire contracts, and runtime-host implementation modules are package-private.

The local plugin package remains private and source-first. Local linking and package inspection are supported; npm publication, marketplace distribution, independent versioning, provenance, and public compatibility policy are separate future work.
